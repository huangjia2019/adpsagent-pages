1. 交付物不是文字，是工程状态

先设想用户打开的不是聊天窗口，而是一台正经的系统建模软件，MagicDraw 或 Cameo 这一类。软件里已经存着一堆构件：包、块、用例、状态。它们会被下游的设计、仿真和文档直接引用，属于正式模型而非草稿。

SysML 可以粗看成系统工程界的图纸语言。九类常见图各管一件事，包图管文件夹怎么分，用例图管谁要用系统做什么，块定义图管系统由哪些积木组成，内部块图管某一块积木内部怎么连线，状态图管有哪些状态和跳转，时序图管谁先发消息谁后回。

案例方强调了一条容易被忽略的事实：在建模工具里，模型库和图是两层。模型库里可以有很多元素，某一张图只是把其中一部分摊到画布上给人看。人自己建图时也遵循同一顺序，先想有哪些对象，再想它们怎么连，最后决定这张图画哪些。

这条事实决定了整个系统的形状，也决定了它和内容型助手的分野。报告用一句话概括产品目标。

用户用自然语言点名要一张图，系统在正确位置写出结构正确、可撤销的结果；说错了就拦或者问清楚，而不是用漂亮话假装成功。

错一位的代价在两类任务里完全不同。报告写歪了，重写一版即可。模型写错了，可能导入成功、画布好看，但引用悬空、范围扩歪，后面所有图都跟着踩坑。这个差别把早期一个很自然的想法否掉了：把建模工具的接口全部暴露给模型，让它自由编排。案例方的结论是，问题不在接口不够，而在于模型不适合独自保管不可错的结构坐标——挂在哪个包、连到哪个已有块、关系两端是谁。这些交给程序和工程索引保管，模型负责在规矩内起草。

2. 一条贯穿例子：一句话建「闸机」用例图

报告用一个小例子串起全部难点，不熟悉建模的读者也能跟着走。用户说：

在「闸机控制」包下建一张用例图：访客刷卡进门、管理员远程开闸、运维人员复位故障。访客和管理员是人，运维是运维系统。

人接到这句话会拆成四件事。挂哪里，「闸机控制」这个包必须已经存在。有哪些东西，三个用例加两个人参与者加一个系统参与者，还需要一个主体说明这张图在讲哪个系统。怎么连，人和系统各自关联到对应用例。图画什么，把上述内容放进用例图画布，而不是把整个工程摊开。

如果让模型一次调用把这些全做完，表面上省事。案例方实测的结果是在引用对不上、漏用例、图画歪之间随机翻车。后面几节都是从这里长出来的。

3. 一次调用生成「元素 + 关系 + 图」为什么更贵

早期提示词大致是「请直接输出完整建模结果：所有元素、所有关系、以及图」。有时能成，更多时候会出现四类故障：关系指向一个话说到了但清单里没建出来的名字；同一角色写了两个近似称呼，线挂在其中一个上，另一个成孤儿；上下文太长，模型后半段开始漏项；图上堆了不该出现的工程杂物，或者该进图的反而没有。

报告把背后的错误直觉点得很准：一次调用等于少延迟少花钱，这个判断对内容生成有时成立，对结构交付不成立，因为失败重试加人工排障才是成本的大头。

解法是按建模手艺把主链拆成三个子能力，边界取自人建 SysML 的自然顺序。

阶段这一步只准想什么落到闸机例子
① 元素包已锁定；建或复用哪些参与者与用例；主体是谁访客、管理员、运维系统；三个用例；主体＝闸机系统
② 关系在上一步的名单上连关联，端点必须已存在访客—刷卡进门；管理员—远程开闸；运维系统—复位故障
③ 视图按用例图规则挑进图内容并生成视图一张用例图，而不是全工程导览

先元素后关系的理由是关系离开端点就不成立。让模型同时发明元素和关系，等于一边造牌一边连线。把元素阶段钉死之后，关系阶段的任务收敛成在一张已知牌桌上连线。视图放到最后，是因为模型库和画布本来就是两层，第三步只做投影和筛选，不重新发明结构。

这套拆法同时解决三件事。每一步目标单一，失败时可以定位到是元素漏了、关系断了还是视图没筛对。Token 自然降下来，关系阶段主要吃元素表，不必把整段需求规范再贴一遍，视图阶段吃筛选规则，不必重新描述对象。子能力边界按建模语义切开，上游产出是下游的契约输入，下游不得偷偷改上游已承诺的标识与归属。

关于这三段是三个子 Agent 还是一条流水线上的三个阶段，报告留了个口子，也把判断说清楚了：重要的是职责边界与数据契约，而不是进程形态。这句话对应到 ADPS 矩阵上是两个格子的差别，第十一节会回到这里。

4. 一次一图：可验收的单次承诺

用户很自然会说「帮我把闸机系统的完整模型建好」。早期系统若顺着这句话自动做完包图、需求图、用例图、块定义图、内部块图、状态图，结果几乎总是范围失控、中间一步歪掉后面全歪、Token 与延迟爆炸，而且验收无法对账，因为「完整」没有客观的完成定义。

产品纪律因此写死为一句话。

一次用户操作 ＝ 一种图类型 ＋ 一个明确挂载位置。

「完整模型」拆成用户驱动的多轮。做完包图，系统可以建议常见的下一步是用例或块定义，但下一句仍由用户点名。九图联调是九次独立操作。回到闸机例子，用户只点了用例图就只交付用例图，即使需求文本里顺便提到了故障状态机，也不擅自去建状态图。

案例方给出的可迁移技巧，是把用户一句话里的野心和系统的单次承诺拆开。野心记进会话摘要当建议，承诺必须可验证、可撤销、可回归。开放域助手喜欢多做一点显得智能，在结构交付里，多做一点常常就是事故。

5. 找不到挂载点时，最危险的是「好心」

用户说在「闸机控制」包下建图，工程里却没有这个包。早期模型会好心新建一棵包树，顺手造几个听起来很完整的父包。画布上看着成功了，工程却被扩脏。

错误直觉是「Agent 应该主动补齐缺失上下文」。在文档助手里这或许是优点，在正式模型库里，静默扩域等于越权。

解法是挂载位置在工程索引里对不上就停，而且尽量停在昂贵的规划之前，然后用人话问。有两三个近似候选就列出来让用户选，超过这个数量再要求更精确的名字。禁止静默默认丢到项目根，禁止为了演示完整而虚构骨架。

这张卡片底部那一行才是重点所在。报告把它总结成一句话：HITL 的难点不是弹窗，是续跑状态机。问一句很容易，问完还记得自己在干嘛才是工程。案例方把 pending 操作做成显式状态，包含图类型、范围、已完成阶段和用户是补充还是跳过。用户补了包名之后从断点继续，而不是重新做一次意图识别，把图类型弄丢，跑去闲聊或者建了别的图。

6. 幻觉里最毒的一种：成功的假结构

大模型胡说句子，用户看得懂。更毒的是写回报告说成功，工程里却没有对应变更，或者变更语义是错的。案例方至少打过五类。

空变更假成功。 用户要求给用例图补上「紧急解锁」，规划或匹配失败，最终增量是空的，早期却仍然返回成功。对策是把「用户要写入」和「实际可写增量」对齐，空增量不算成功，本来就是那样的幂等跳过除外。报告这句话值得单独摘出来：验证语义必须等于写回语义。

关系悬空。 元素表里没有「紧急解锁」，关系表却连了一笔。对策是关系阶段的契约规定端点必须落在本轮元素结果或工程可复用集合里，门禁扫一遍，修不了就拦。

漏项却装作完整。 用户点名三个用例，只产出两个。对策分两种情况：能从用户话里结构化数得清的清单，写前对照计划数量，少了就澄清或阻断；数不清的时候不要假装很懂去硬拦，放行后写回时用一句降级警告说实话，让用户下一句补。

视图撒谎。 模型库里有对象，图上没有；或者图上出现了不该进本图的东西。对策是第三阶段单独做按图类型筛选，验收以画布与模型结构为准，不以聊天自述为准。

编造挂载与复用。 即第五节那一类，元素阶段就用工程索引核对，能复用的标记复用，找不到范围就阻断。

处理这些问题时，案例方把质量分成三类，策略才写得死。

类型含义谁处理
结构可判定类型非法、引用可确定纠正、层放错程序自动修或阻断
用户说过但模型漏了明确列举未兑现写前问或写后警告，禁止瞎猜补全
品味与建议粒度粗细、要不要某条最佳实践忽略或等用户下一句

还有一条硬规矩：绝对不用行业词表在程序里猜语义。今天演示的是闸机，明天换成化工装置，词表会把维护拖死。程序只认类型、引用、归属、白名单这些结构事实。

三种结果的用户可见形态被刻意做成三张不同的脸。

7. 砍掉模型自评闭环，换上写回前门禁

案例方早期做过一版「生成 → 让模型写评审意见 → 再改 → 再评」。这套在这个场景里三头受挫：评审提示词和生成提示词的口径互相打架，评审按教科书骂，生成按工具 schema 写；链路又慢又贵，还可能空转；用户被一堆「不足与风险」长文淹没，图却还卡在确认门外。

最终的取舍是对用户默认自动写回加一步撤销，像代码补全那样，画布即结果。对质量则用确定性门禁，组装前最多一轮结构修复，修不了就不写入。写回后的模型自我评审循环被整个砍掉，用户不满意就用下一句对话改，而不是让机器自己开会。

报告给出的判断是：看起来很 Agent 的反思环，不一定比编译器式门禁更适合结构交付。反思适合开放文本，门禁适合必须可导入、可回归的工件。把随机性预算花在规划草案上，把确定性预算花在能不能进库上。

这是本案例与前两份报告最值得对照的一处取舍，第十二节会展开。

8. 白名单差点把自己绊死

这是个很脏但很真实的细节，外行也能听懂。建模工具的导入层有时会把细类型收成粗类型，好比身份证上只写「连接」，业务上却要区分普通连线和参数绑定线。如果门禁只用收粗以后的名字去对白名单，就会出现三段错位：规划阶段明明写了对的细类型，校验时被收成粗类型，粗类型不在本图允许列表里于是被误杀，或者反过来被放进错误的桶。

解法是白名单匹配要承认细名与粗名在导入语义上等价的双向关系，并按图类型选对结构模板，而不是用字符串全等一行搞定。

案例方把这一条提炼成通用规则：凡是「LLM 规划的类型」和「工具写入的类型」不是同一套词表时，中间必须有显式等价层。 这类 bug 极其隐蔽，日志看起来像模型在胡写，实际上是自己的校验把合法结果翻译坏了。这一段在整份报告里技术含量最高，也最容易被抽象架构图掩盖掉。

9. Token 治理是产品纪律的副产品

工程一大、历史一长，再把九种图的规范全文塞进每一次调用，截断、漏项和答非所问会一起出现。换更大的窗口只能推迟爆炸。案例方的做法是一套组合拳，六条都不是运维补丁，而是产品与工序纪律的直接结果。

一次一图，只带当前图画像。三阶段拆分，每阶段只带该阶段规范加上游结构化结果。分析做一次，关系与视图阶段吃摘要，不反复重读用户长文。工程上下文分层，远处只给一张「这轮会话做到哪了」的提纲，近处才是邻近包、邻近块和可复用元素名单，切硬边界时要可观测，宁可知道少了什么也不假装全看见了。模型分流，意图、澄清和简单填表走轻模型池，复杂的元素与关系规划走主模型，视图筛选能规则化就不必事事上最贵的模型。按图复杂度路由，包图可以压缩分析，时序图和状态图才把三阶段跑饱。

三段拆开看似多了几次调用，案例方实测常比一锅炖失败再整锅重来更省，也更稳。报告的收束是：先问这一步决策依赖哪些字节，再拼上下文。上下文工程的本质是删减，子能力拆分是删减的结构手段，不是为了多画几个 Agent 框。

10. 真实运行现场

前面九节的示意图由案例方用 SVG 绘制，用于说明交互形态。这一节放三张真实运行截图与两段演示录像，用来对照示意图与实际系统之间的距离。

下面这条日志比任何架构图都更能说明意图收敛这一步在做什么。它来自演示录像中用户提出一个纯咨询问题的时刻。

两段录像分别是三分钟的概览和十四分钟的完整走查。短片带中英文字幕，从数据清洗、意图确认一直到出图。长片走完了卫星平台从需求到内部块图的多轮建模，通知窗口里可以看到每一次 LLM 调用与每一条校验规则的执行。

按行读这张表，结果相当集中。治理行四格全实，反思行两格是主动否决。 这个系统把本该花在自评环上的预算，整体换成了门禁、撤销、承诺边界和可观测性。行动行四格全实则说明主干在执行侧，三阶段链、工具白名单、护栏与编排各占一格。

按列读，链式与层级两列最重。链式承载工序，层级承载治理。并行与循环两列几乎是空的，这与结果必须可导入、可回归的任务性质一致：并行会让写回冲突，循环会让延迟不可控。

12. 三份案例报告的交点

把这份报告与前两份放在一起读，会发现三个来自完全不同行业的团队在同一个地方作出了同一个决定。

案例行业不让模型生成的东西
报告 01 · 东方屹腾企业 SaaS 流程自动化长随机 ID 等机械参数
报告 02 · 成都玄宿地理信息与数据服务workspace、store、SRS、bbox 等发布参数
报告 03 · Ark · 雅格MBSE 与工业软件稳定标识、引用端点与挂载位置

三个团队用的词不同，指的是同一类东西：那些错一个字符就让下游失败、而且失败往往不在当场暴露的机械坐标。ADPS 把这条分野写进了执行型与内容型与机械状态平面两个概念定义。两个独立案例支持一条观察，三个来自互不相干行业的独立案例支持同一条观察，性质就不一样了。

更值得注意的是三者的分歧点。报告 02 建了失败日记，把跨运行的失败沉淀成规则供下一次查询，落在记忆 × 循环。报告 03 把自评闭环整个砍掉，反思行两格主动留空。这个差别不是水平高低，而是失败信号的可判定性和时延要求不同。玄宿的发布结果可以在离线时段由外部探针判定对错，失败沉淀有时间做；雅格的写回发生在用户等待的交互回合里，判定必须当场完成，于是确定性门禁比模型自评更合适。

换句话说，要不要上反思环，取决于错误能不能被离线判定，而不是取决于系统的智能程度。这条判据由两份报告的对照才浮出来，单看任何一份都得不到。

13. 迁移边界

案例方自己划出了适用与不适用的两侧，这里照录并稍作展开。

适合迁移。 结果要进正式系统，结构约束强，错一位会伤到存量工程，工具链封闭可治理。除 MBSE 外，EDA、BIM、ERP 主数据、配置管理数据库和工艺路线编排都符合这几条。可以搬走的是四件事：单次承诺的验收口径，按领域自然工序拆子能力并用契约衔接，结构坐标进程序与索引，以及验证语义对齐写回语义。

案例方给出的十条可迁移清单里，有三条在其他两份报告中也独立出现过，可视为跨案例的稳定项：假成功比失败更糟；澄清是状态机不是多轮聊天；可观测性要在开发期就做。

不适合迁移。 主要产出是报告、课件或者开放检索拼装的场景，步骤松散、文本漂移可接受，硬上这套门禁和三阶段写回属于过度设计。判断标准很简单：如果一次输出错了只需要重写一版，那么反思环大概率比门禁划算。

报告最后一段的自我总结值得原样保留。案例方一度以为难点是让模型更懂 SysML，后来发现更难的是承认模型是概率引擎却要交付确定性工程状态，忍住多做一点的产品冲动，把人在工具里本来就会的建模顺序翻译成可调度、可续跑、可回归的子能力，在用户体验上像补全工具，在内核上像带门禁的编译流水线。方向并不炫：少承诺、严校验、可撤销、可续跑。
