1. 传统 GIS 发布流程的约束

GIS 数据发布需要依次处理格式识别、坐标系、样式、瓦片缓存和图层组。各环节包含需要人工选择和配置的参数，部分错误不会在配置阶段直接报告。

玄宿科技从事 GIS 软件产品与系统研发，并拥有自主知识产权的国产化二次开发框架。团队将原有发布流程归纳为三类约束。

跨工具顺序依赖。 数据需要在桌面 GIS、GDAL 命令行、GeoServer 管理界面和 GWC 配置页之间流转，操作顺序和参数依赖人工记忆。重复执行后，很难定位具体哪次运行、哪个步骤发生偏差。

领域知识难以复用。 以 S-57 电子海图发布为例，一组海图导入 PostGIS 后会按物标类生成上百张表，需要逐表创建 store、逐类发布图层，再按顺序组成图层组。图层组若配置为 OPAQUE_CONTAINER，成员图层会从 WMS 列表消失，直接 GetMap 返回 LayerNotDefined；该 ServiceException 的 HTTP 状态仍为 200，只检查状态码会误判为成功。此类平台行为如果只保留在操作人员记忆中，后续同类数据仍需重新排查。

缺少自动验收。 手工发布只能证明操作者在某一时刻打开过服务。系统没有持续生成可查询的验收证据，故障通常由用户反馈后才被发现。

这三类约束与是否使用 AI 无关，分别对应长链路、机械参数和静默失败。

2. 运行期模型的适用性判断

团队没有采用“将 GeoServer REST API 包装为 MCP 工具，再由模型运行时选择接口和参数”的方案。GIS 发布步骤之间存在严格的参数绑定和状态依赖。

workspace、store、layer、SRS 和 bbox 都由上一步产生，并在下一步逐值引用。若由 LLM 重新生成这些机械参数，单个字符或数值偏差可能导致发布失败，也可能在发布成功后产生错误渲染。

案例报告 01 东方屹腾也将机械参数从模型生成内容中分离。两个案例均属于执行型系统：步骤之间传递机械参数，模型负责形成控制信号，不负责生成这些参数。相关定义见执行型与内容型。

场景分类使用以下四个维度。

维度 内容生成型 执行型
步骤关系 松散，顺序可调 严格依赖，跨一步全盘错
步骤间传递 文本内容，语义偏差不致命 机械参数（id、名称、坐标），错一位即事故
错误代价 内容质量下降，一般无副作用 交付失败或破坏业务数据
对模型的要求 生成质量 确定性，而确定性不能只靠概率

GIS 数据发布符合执行型特征：六个阶段存在硬依赖，阶段之间传递 layer_name、processed_crs 和 processed_bbox 等机械真值；发布结果由前端直接消费，GetTile 全部返回 400 即构成生产故障。

3. 推理资产化

执行型系统需要确定性输出，而模型调用具有概率性。该案例在运行期不调用模型，所有运行期决策由规则和静态管线完成。

路由由约二十行查表代码实现，重试与回退由两张 YAML 规则表实现，编排采用静态六阶段链。模型只用于新管线设计：Coding Agent 生成草案，经人工审阅、显式首跑和认证后，活跃管线在运行期按规则执行。

该设计成立的条件是意图可由数据签名确定。目录包含 .000 文件时路由到 S-57 海图管线，包含 .tif 时路由到栅格管线。输入签名即意图，因此意图识别可以使用确定性判定；未匹配签名时返回显式错误。

案例方将这种做法称为推理资产化：管线选择和发布方法在设计期由模型与人员共同确定，结论写入管线声明，运行期查表执行。模型调用成本发生在设计期，产物以 YAML 规则长期复用。

决策依据是频率和开放程度。

决策 特征 归宿
复用哪条管线 高频、有标准答案 规则下沉：管线声明 accepts，运行期查表
失败后怎么办 高频、错误签名可枚举 规则下沉：error_map 加 retry_policy，按签名路由
发布成什么 管线设计期一次性决定 写死在 produces / publish 字段
生长还是复用 低频、一次性、需要领域知识 模型加人，发生在生长期

在 ADPS 双轴框架中，运行期推理被前移到设计期，运行资源主要投入治理和记忆。系统只处理已认证管线覆盖的输入签名，其他输入明确拒绝。

案例边界： “运行期零 LLM”只描述运行路径。管线设计、错误规则沉淀和新格式识别仍由模型与人员共同完成。该系统优先优化单次运行的确定性和成本。

4. 系统的 Agent 属性

运行期没有模型，路由采用查表，编排采用静态链，因此需要说明该系统与普通自动化脚本的边界。

分类依据是结构属性。普通脚本通常采用 fire-and-forget 线性执行；该系统包含感知、决策、行动、验证、回退和能力生命周期。

  • 感知：意图从数据里读出来，不靠人传。validate 阶段按活跃管线的 accepts 声明遍历输入目录，自行识别格式签名。
  • 决策：查表实现确定性决策。新管线注册后，路由自动覆盖新签名，无需修改平台代码。
  • 行动：publish 阶段调用 GeoServer REST、写入 PostGIS 并更新托管目录，产生可观察的外部副作用。
  • 验证：verify 阶段主动执行 GetMap/GetTile 请求和截图，成功条件为 HTTP 200 且 content-type 为 image/*。ServiceException 同样可能返回 200，因此不能只检查状态码。
  • 回退：失败按错误签名匹配回退步骤；未知错误显式上抛，不静默吞掉。
  • 记忆与生长：状态落盘成磁盘事实，失败沉淀成知识卡，管线走 draft、candidate、active 生命周期。能力集合随使用扩展。

与常规 CI/CD 流水线相比，该系统会识别输入签名、选择管线、验收 GIS 领域结果，并将失败沉淀为后续运行可消费的规则。

该系统采用有界自主：意图空间封闭，签名之外明确拒绝；已接受任务要求执行结果可验收、失败可追踪、规则可复用。

5. 磁盘事实平面

系统主干是六个阶段组成的固定流水线：validate 识别格式与路由管线，process 重投影并归一坐标系，generate_sld 生成模板样式，publish 过契约门禁后落 GeoServer，viewer 生成浏览页，verify 截图与请求验收。

每个阶段是独立子进程。编排器通过 subprocess 启动阶段，只接收返回码和输出文本，并按错误签名判断成败。阶段状态通过磁盘文件传递。

阶段状态写入 metadata.json，并遵守一个事实一个写入者：validate 写识别结果，process 追加处理结果，下游阶段只读不重算。bbox 只由 process 计算一次，避免本地重算与落盘值发生漂移。

磁盘事实平面包含三层：metadata.json 保存管线契约，run-state.json 保存编排状态，verify_report.json 保存验收结果。各层通过指针关联，不复制事实。控制台使用这些 JSON 和三份索引投影作为数据源，静态托管，不设置 API 层。

该设计提供四项能力。可审计：阶段边界对应文件边界，运行记录不依赖进程内存。可恢复：重跑时读取落盘输入路径，已成功数据集按状态跳过。可热更新：执行代理为写操作启动新子进程，下一次运行读取磁盘上的最新代码。跨语言消费：前端控制台、执行代理和命令行只共享文件契约，不共享实现代码。

相应代价是文件契约需要人工维护。前端使用时间戳加 5 秒容差判断轮询状态是否属于本次运行，命令行修改时间精度时必须同步更新前端。validate 无匹配管线时使用固定错误前缀，规则表按该前缀匹配。每个状态文件携带 schema 版本号，字段变更时同步 bump。

案例边界： 文件契约依赖 schema 版本、防复发注释和单元测试，缺少编译期的跨端一致性检查。

6. 失败记录与规则闭环

ADPS 将 M4 失败日记定义在记忆 × 循环坐标。该系统以知识卡片、两张规则表和带质量门的管线生命周期实现三层循环。

内层为运行期秒级循环，不调用模型。 阶段失败后匹配错误签名，动作只有 retry、abort、skip 三种。例如，“源矢量缺少空间参考，无法判定坐标系”对应 abort，“WMTS 瓦片图层启用失败，可能缓存服务未就绪”对应 retry。缺少空间参考、海图更新链断号等失败不允许自愈，必须显式停止。

外层为沉淀期周级循环，包含人工审核。 每次实际失败写入一张五段式失败卡。以“WMTS 瓦片请求除零报错”为例：signature 记录 GetTile 返回 400 且响应包含 / by zero；root_cause 记录 metatile 尺寸被配置为 0×0，并说明官方文档未描述该取值的后果，该结论来自平台实测；fallback 记录即时处理；fixed_by 将结论写入 SDK 默认参数；related_rules 关联运行期规则表。

项目协作约定要求：涉及领域知识或平台机制的修复，必须同步写入失败卡或规则条目。验收条件是后续人员或 Agent 能否通过卡片定位同类现象。

知识卡分为六类：capabilities 记录管线能力，profiles 记录数据画像与处理基线，patterns 记录跨管线约束，failures 记录五段式失败，decisions 记录平台取舍与理由，refs 记录组件行为基线。能力卡与管线同名，其余卡的 source 字段包含管线路径，控制台按这些规则生成知识视图。

7. 管线生命周期与认证

中层为生长期天级循环，模型只参与脚手架生成。 ADPS 将管线类构件映射到 F2 技能包。该案例进一步实现技能包的生成、验证和认证过程。

管线从脚手架进入自动运行需要通过两类质量门。证据门：首次运行由人员显式触发，完整执行六个阶段；publish 前检查最小事实集，结构校验失败时禁止调用 GeoServer；verify 发送真实请求并执行截图与图像分析。首跑成功后状态自动转为 candidate。认证门：candidate 升级为 active 必须由人员确认。

版本漂移监控比较活跃管线当前版本与已认证版本。两者不一致时，系统自动将管线退回 candidate，要求重新验证和认证。

HITL 只位于两个动作：新管线首次运行由人员显式指定，candidate 升 active 由人员认证。模型生成管线草案，人员决定是否允许自动运行，系统阻止未认证管线自动接收任务。

三层循环分别处理运行期可恢复失败、管线能力生命周期和跨运行失败沉淀；外层生成的规则供内层运行期查询。

9. 架构取舍与失效信号

下表记录各项架构取舍、收益和需要重新评估的失效信号。

取舍 放弃了什么 换来什么 失效信号
运行期零 LLM
（推理资产化）		 开放性：未匹配签名的输入明确拒绝 每次运行确定；零模型边际成本；每个决策可审计到规则行 意图载体从数据签名变成开放对话；签名空间膨胀到规则表维护不动
顺序链
（不做并行）		 吞吐 任何一次运行可精确复现；资源竞争类抖动从「回归」降级为「已知现象」 批量规模大到排队不可接受
单 Agent 加人机分工
（不做多智能体）		 多角色并行协商、对抗评审 权责链短：每个决策能找到唯一的责任人或机制 出现开放性强、需要多视角对抗判断的任务类型
静态编排
（无运行期重规划）		 运行期自适应 新增数据格式编排层零改动；执行计划可在设计期评审 链路需要按数据特征动态分叉
磁盘事实平面
（文件即状态）		 跨机扩展、多租户并发写 可审计、可恢复、热更新、跨语言消费 部署形态从单主机单租户变成多机多租户

这些取舍相互关联。运行期引入模型后，计划会依赖模型的即时判断；引入并发后，“一个事实一个写入者”需要增加锁或事务；引入多租户后，文件契约需要迁移到支持并发和隔离的存储介质。

架构评审的主要问题是：确定性优先这一前提是否仍符合当前场景。

系统保留了相应运行证据。两个数据集并发发布时，其中一个数据集的 verify 曾短暂出现零个瓦片请求成功。案例方将其记录为“已知瞬时抖动”，没有修改顺序管线。该平台以排队控制吞吐，避免并发引入资源竞争。

系统明确拒绝未被已认证管线覆盖的输入。GeoJSON、KML 当前均返回“无匹配管线”。新格式需要经过管线设计、首跑验证和人工认证后才进入能力清单。

10. 迁移条件与限制

本文的全部主张只在这一章的约束清单内有效。

可迁移机制。 高频且有标准答案的决策可以下沉为规则表，低频开放决策保留模型并移出关键路径；发布前校验最小事实集，发布后用真实请求验收；失败日记采用固定五段结构并回链规则；能力使用生命周期和版本漂移监控；进程间可通过事实平面交换状态。

成立条件。 1. 意图空间可以封闭枚举。输入签名无法表达自然语言意图时，需要重新引入运行期模型，将意图转换为枚举控制信号；机械参数仍由工具和状态提供。2. 错误代价达到执行级；仅影响内容质量时，这套治理成本可能过高。3. 错误签名可以枚举；失败模式开放时，规则表只能作为日志。4. 链路重复发生；一次性任务难以获得沉淀收益。

不可直接迁移的内容。 错误规则和失败卡来自 GIS 与 GeoServer 的具体行为；双轴矩阵中的空格由本案例约束决定；“运行期零 LLM”也是当前意图空间下的实现结果，不能作为其他场景的默认目标。

针对第一章的三类流程约束，系统将链路固化为平台和管线，将领域知识写入规则和卡片，并将验收设置为每次运行的必经阶段。

双轴矩阵中包含 14 个实格、4 个薄格和 1 个官方空白格实现，其余留白。每个落位均可依据代码实体和运行证据重新评估。

与案例报告 01 的对照

案例 01 东方屹腾面向企业 SaaS 业务流程自动化，意图来自自然语言，因此运行期保留模型，并以机械状态平面承载业务参数。玄宿科技面向领域数据处理发布，意图来自数据签名，因此将运行决策前移到设计期。
