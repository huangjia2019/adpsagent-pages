1. 执行型与内容生成型的系统边界

东方屹腾是一家企业 SaaS 公司，产品覆盖人事、组织、考勤、审批和薪酬，并连接银行与税务系统，支持算薪、代发和报税。目前，这套产品矩阵已服务两万多家企业。

团队最初考虑把现有 API 按 MCP 协议封装为 MCP Server，再由 Agent 完成业务流程。原型验证很快暴露出一个边界问题：通用工具调用通常允许模型根据上下文组织参数，东方屹腾的核心场景却要求多个业务 API 严格传递状态。薪资组配置、考勤组配置、算薪代发和员工入职都包含连续操作；其中的实体标识、依赖关系和执行顺序必须准确。

以报销流程为例，常见步骤是创建申请、上传发票、提交审批和查询结果。GUI 程序会把刚创建的申请 ID 直接传给发票上传接口。改由 Agent 执行后，这个 ID 仍须来自上一步的真实回执，不能从自然语言上下文重新生成。团队曾把每步工具回执追加到上下文，再让模型组织下一步参数。测试结果存在偶发的 ID 误写和参数错绑。JSON Schema 可以约束字段类型和格式，却不能证明参数来自哪一次调用。

因此，团队把目标系统区分为两类：

  • 内容生成型 Agent：步骤之间主要传递文本，适合资料检索、报告生成、PPT 生成和内容评审。局部语义偏差通常可以在后续生成环节修正。
  • 执行型 Agent：步骤之间传递业务状态，任何漏步、跨步或参数错绑都可能造成任务失败或数据破坏。

MCP 仍适合开放工具发现和内容型协作。东方屹腾需要补充的是一套面向执行流程的状态、调度和治理机制。这个分类决定了后续架构。

2. 业务目标与首个场景

团队首先评估了用工分析、薪酬结构优化和考勤报表分析等候选场景。这些场景容易演示，但并未覆盖客户使用系统时的主要阻力。东方屹腾的客户以中小企业为主。访谈显示，新客户最困难的环节是首次配置：建立薪资组和薪资项、导入员工与组织、完成定薪，并配置考勤和审批规则。

同一套产品在两类客户中的反馈差异明显。由运营交付团队完成初始配置的客户，通常能在第一个月顺利使用；自行配置的客户更容易在启用阶段中断。部分客户还希望把每月核对、算薪、代发和报税继续自动化。

典型需求可以表述为：企业计划以每月 1 万元的综合成本使用一名员工，希望系统自动拆分基本工资、补贴、奖金、社保和公积金，并完成后续发放与申报。客户关注综合成本和合规结果，系统负责维护底层业务数据。

团队据此把“薪资组快速搭建”确定为第一个锚点场景。它范围明确，同时覆盖意图理解、模板匹配、连续 API 调用、状态传递、失败回滚和人工确认，足以检验执行型 Agent 的关键机制。

3. 渐进式实施与可观测性

后端使用 Go，初期没有引入 Agent 框架。第一阶段只接通连续对话、附件上传和回复流，暂不实现完整的技能注册与工具编排。这样可以先固定输入输出契约，再逐步增加推理和行动能力。

Web 界面与后端同步建设。对企业项目而言，界面不仅承担最终交互，也用于业务评审、阶段演示和问题复现。团队可以在同一页面核对用户输入、执行过程和结果，业务人员也能尽早验证流程是否符合实际操作。

可观测性从第一阶段开始进入运行时设计。一次对话被拆成按时间排序的 Activity；每个 Activity 下包含一个或多个 Frame，记录运行态提示词、模型输出、工具调用、耗时和成本。意图识别、网关路由、ReAct 循环等程序动作均发布为带语义的结构化事件。开发环境显示完整时间线，生产环境可按权限关闭调试详情。相关实现见 G4 可观测性切片。

至此，系统具备连续输入、结构化事件和运行过程回放能力，可以在稳定接口上增加后续模块。

4. 控制平面与叙事平面

第一个新增模块是意图识别。它接收用户对话，通过结构化输出生成下游可以消费的控制信号。早期系统定义了三类意图：

  • chat：领域外闲聊，直接结束或返回固定答复；
  • analyze：业务知识咨询，检索领域知识后生成回答；
  • resolve：需要推理、规划和工具执行的业务任务。

解析失败时统一返回 unknown，由下游执行兜底逻辑。后来，团队根据业务路由把信号扩展为 task、information、produce、chat 等类型。

这一实现形成了两个并行平面：

  • 控制平面保存意图类型、路由结果、任务状态和准入信号，用于驱动程序分支；
  • 叙事平面保存用户请求、分析结论和执行摘要，为模型推理提供语义上下文。

这个划分与分布式系统中的控制平面和数据平面类似。模型负责把自然语言收敛为有限的结构化信号，程序根据这些信号执行确定性逻辑；执行结果再写回叙事上下文，供下一次推理使用。控制信号和叙事内容采用不同的数据结构、校验规则和持久化策略。意图识别的进一步设计见 R2 复杂度路由切片。

5. Orchestrator 与意图网关

Orchestrator 负责一次会话的运行时编排。它接收用户输入，读取控制信号，调用推理、记忆、知识检索和行动模块，并在任务完成后合成回复。各能力模块通过明确的输入输出契约注册到 Orchestrator。

系统最外层保留一个轻量的 MessageHandler。它接收用户消息并调用 Orchestrator，同时订阅统一活动事件，通过 SSE 向 Web 界面推送执行进度和回复。这样，界面呈现逻辑与运行时控制分开，Orchestrator 只处理流程和状态。Go 的协程与通道用于实现事件发布和订阅。

意图网关消费意图识别结果，并选择对应执行链。chat 可以直接结束，analyze 进入检索与回答链，resolve 进入推理和行动链，unknown 进入兜底流程。整个会话分为三个阶段：

  1. pre：接收原始输入并完成意图识别；
  2. middle：按控制信号编排具体能力；
  3. post：合成结果并向用户返回。

这个边界使新增能力可以接入 middle 阶段，而不改动入口、流式输出和结束协议。

6. 链式推理与控制信号

resolve 只表示请求需要执行，尚未给出可操作的下一步。系统使用链式推理逐步收敛任务：每轮读取上一轮结果，直到模型返回完成信号或达到步数上限。

推理输入由 ReasonContext 统一组织。它同时包含用户原始请求、意图识别结论、已有进展和当前可用能力。推理输出采用结构化数据，至少给出下一步动作类型，并映射到程序内可调用的逻辑，例如检索知识、调用技能、进入任务规划、继续推理或结束会话。

这里仅决定下一步动作。工具执行会改变业务状态，后续动作需要基于最新回执和当前目标重新判断。完整计划只在任务依赖已经明确时生成。相关实现见 R1 思维链切片。

7. ReAct 与工具执行

当下一步动作仍需要边执行边判断时，系统进入 ReAct。每轮由 Thought、Action 和 Observation 三个结构组成，并作为一个 block 追加到 scratchpad。下一轮读取已有 block chain，结合最新观察继续推理。

Action 可以调用工具、检索知识或再次调用模型。工具调用由行动模块封装，Orchestrator 只负责模式切换和控制权交接。这样，调用前校验、状态解析、调用后检查和失败处理可以与具体工具一起演进。

控制信号由业务场景定义。除继续、完成和失败外，系统也可以定义立即终止、转人工或转规划执行等信号。工具选择与机械状态坐标的设计见 A1 工具调度切片。

8. 规划执行与任务状态机

早期工具与技能先使用生产级接口契约和模拟数据接入，以验证 Agent 能否召回正确能力。薪资组快速搭建的模拟流程包含四个连续步骤：匹配薪资组模板、创建现有数据快照、导入模板、失败时按快照回滚。

团队最初把步骤说明作为技能上下文交给 ReAct。测试中出现过跨步和漏步，说明仅靠语义提示不能稳定维护严格依赖。系统因此增加规划执行模式，在执行前把任务拆成 DAG，并通过状态机管理节点。

规划执行包含任务图、规划器、执行器、验收器和节点状态机。下游节点只有在所有上游节点为 completed、自身为 ready 时才能调度。并行节点也由同一组状态转换规则管理。

ReAct 与规划执行按任务状态切换。任务边界尚不明确时使用 ReAct 探索；依赖关系明确后，控制权返回 Orchestrator，由规划执行维护顺序和验收。详细设计见 A2 规划执行切片。

9. HITL 阻塞与恢复

任务状态机为人在回路（HITL）提供了基础。敏感操作开始前，执行器把节点置为等待审批；人工通过后，系统从持久化状态恢复上下文并继续执行。

HITL 有两种常见形态：

  • 叙事续作：本轮会话结束，用户在下一轮输入“继续”或“确认”，系统根据会话上下文恢复任务；
  • 执行流阻塞：当前会话保持运行，任务节点暂停并等待审批事件，收到批准后从原节点恢复。

第二种形态需要持久化节点状态、任务图状态和下游依赖。规划执行模块已经提供这些结构，因此审批策略只需声明哪些任务或工具必须阻塞，并把审批结果写入状态机。相关实现见 G1 审批门切片。

10. 机械状态平面

接入真实 API 后，团队再次遇到参数传递问题。第一步根据用户 ID、企业 ID 和业务目标匹配模板，接口返回 template_id；后续导入接口必须使用同一个值。企业系统中的 ID 常由雪花算法或其他方案生成，长度可达 64 位或 128 位。模型即使在上下文中看到该值，也可能在重新输出时误写字符。

这类错误有两种后果：格式校验发现错误并终止；错误值恰好通过校验，导致任务作用于错误实体。后一种风险要求系统同时验证参数值和参数来源。

团队没有找到能直接复用的公开实现，于是增加机械状态平面。工具回执中的业务状态由程序解析和保存，后续工具按坐标读取，不经过模型重新生成。叙事上下文仍可记录“已匹配模板”等摘要，但不再承担 ID 传递。

该方案依赖一个前提：系统是由企业管理的封闭工具体系。工具注册表在运行前已知，因此 Agent 启动时可以建立状态键字典。系统级状态在登录等关键事件写入，API 级状态由工具调用产生。

每个工具声明机械状态依赖，包括参数名、作用域、生产工具和运行层级。工具既可以生产状态，也可以消费状态。SessionState 维护由作用域和键名确定的 Cell；每个值同时保存 Provenance，记录生产者、调用实例和来源回执。消费者按坐标读取，并在调用前校验来源。

执行链路由五个部件组成：

  • Skill 声明业务 SOP；
  • Workspace 维护任务顺序；
  • Tool 声明状态生产与消费；
  • SessionState 保存值和 Provenance；
  • RunPipeline 统一解析、校验和注入参数。

这套机制不要求改造原有 SaaS API。API 通过网关注册后，Agent 可以按场景组合调用；严格参数由程序传递，模型处理意图、语义和计划。工程实现见 A1 工具调度切片。

11. 会话统一状态平面

随着叙事状态和机械状态被分离，规划执行中的任务状态也被单独整理。最终的会话运行时包含三个状态平面：

状态平面 回答的问题 主要数据 持久化真源 主要读取方
SessionNarrative 用户要求什么，当前进展如何 原始目标、摘要、经验和上下文投影 Anchor 与 Ledger 推理、记忆和回复合成
SessionState API 参数来自哪里，是否有效 scope、key、value、producer、provenance Timeline 事件物化的 Cell RunPipeline、治理和前置校验
Workspace 哪个任务可以执行，是否完成 DAG、节点状态和依赖 任务图与状态迁移记录 规划器、调度器和执行器

任务执行产生的叙事摘要写入 SessionNarrative，业务参数写入 SessionState，节点状态写入 Workspace。三个平面可以通过统一事件关联，但不混用数据职责。

这个划分解决了三个不同问题：语义上下文供模型理解，业务参数供程序精确读取，任务图供调度器控制顺序。相关切片见 M3 进度追踪 和 P1 上下文分诊。

12. 叙事状态：锚、账、集

SessionNarrative 用于维护目标与进展，由 Anchor、Ledger 和 Collection 三类数据组成。

锚（Anchor）保存用户在会话或任务入口提交的原始目标。长链路中的推理、行动和压缩都会改写信息形态，后续推理仍需显式读取原始目标。用户只输入“继续”时，锚也用于恢复该指令所指向的业务目标。

账（Ledger）按时间追加关键进展。每个重要推理或行动完成后，系统把结果压缩为可检索的事件摘要，记录完成了什么、产生了哪些结果以及仍有哪些约束。

集（Collection）是在关键推理入口按当前任务从 Ledger 投影出的临时上下文。它只选择与当前步骤相关的事件，并与 Anchor 一起注入模型，控制上下文长度。

Anchor 保持目标稳定，Ledger 保留过程事实，Collection 提供当前步骤所需的最小语义视图。上下文投影见 P1 上下文分诊，进度语义见 M3 进度追踪。

13. L1/L2/L3 分层记忆

团队把记忆分为 L1、L2 和 L3。L1 服务当前执行上下文，L2 保存可追溯的历史事实，L3 保存从成功或失败任务中提炼的经验。L3 使用向量索引召回相似经验，并保留指向 L2 原始事实的 ID；需要核对详情时再加载 L2。

例如，历史任务已经验证某个 Skill 可以处理相同场景，新的推理可以优先选择该 Skill。若某个接口曾在中间步骤失败，规划器可以先调用健康检查，再决定是否执行成本较高的前序任务。

记忆召回集中在链式推理首次调用、ReAct 首轮和任务规划等能力边界，避免每一步都检索。这个安排与操作系统按需加载内存页的思路相近：常用上下文留在近端，历史事实持久化，经验通过索引按需加载。详细设计见 M1 分层保留切片。

14. 架构全貌与迁移条件

东方屹腾的实现可以概括为一条逐步扩展的运行链：

  1. ChatLoop 接通对话、附件和流式回复；
  2. Activity 与 Frame 提供运行过程观测；
  3. 意图识别把自然语言转换为有限控制信号；
  4. Orchestrator 与意图网关选择执行链；
  5. 链式推理和 ReAct 处理逐步收敛的任务；
  6. 规划执行用 DAG 与状态机管理严格依赖；
  7. HITL 在敏感节点阻塞并恢复；
  8. SessionState 与 Provenance 保证参数来源；
  9. SessionNarrative、SessionState 和 Workspace 分别管理语义、参数与调度；
  10. Anchor、Ledger、Collection 以及 L1/L2/L3 记忆维持长程任务上下文。

这套架构适用于步骤明确、依赖严格、需要连续传递业务状态的执行型场景。若漏步、跨步或参数错误会导致交付失败或业务数据损坏，任务图、状态机和机械状态平面具有直接价值。机械状态平面还要求工具由组织统一注册和管理，以便在运行前确定状态键、来源和作用域。

资料检索、总结和报告生成等内容型场景通常允许更松散的步骤和文本传递，可以优先采用 MCP 等开放工具协议，不必同时引入完整任务图和机械状态平面。迁移前应先确认错误成本、状态依赖和工具边界，再选择相应机制。
