模式简介 结构化记录失败步骤、错误、根因和补救措施，并在后续相似任务中主动召回。

问题

许多 Agent 系统保存任务进度，却不跨会话保留失败记录。会话结束后，错误现象、错误判断和补救过程随 context 一起消失，后续相似任务可能重复同一错误。例如，Agent 完成主任务后将测试环境配置写入生产配置，之后又在另一个项目中执行了相同操作。

失败日记将这类事件保存为可检索记录。新任务开始前或高风险工具调用前，系统召回相关记录，把已知失败条件和处理方法注入当前 context。

坐标说明：记忆 × 循环

  • 纵轴 · 记忆：它把"失败"作为持久化学习材料跨调用累积，是长期记忆里的反例库——一面记成功（程序性记忆），一面记失败（失败日记）。
  • 横轴 · 循环：失败记录在本次任务写入，在后续任务读取并更新，形成跨调用的 outer loop。

解决方案与机制

失败日记包含检测、分类、记录和召回四个环节：

  1. 检测 Detection：判断这次任务算不算"失败"。包括任务级失败，也包括信息检索本身的失败（如 RAG 索引滞后、漏检、误检——这些是 LLM 时代新增的失败类型）。
  2. 分类 Classification：归到哪一类失败。生产实现可区分临时性与永久性、客户端与服务端、payload 与 context、通用与厂商特定、可恢复与不可恢复，并为每类配置 recovery strategy。
  3. 记录 Recording：结构化存档，schema 必须比自由文本强。一条失败记录至少含任务指纹、类别、一句话总结、根因、补救动作、可执行的 lessons。
  4. 召回 Recall：新任务开始时按相似度检索历史失败并注入 prompt。try-catch 处理当前调用中的异常，失败日记则跨任务保留和复用失败信息。该路径在 inference 阶段使用，无需重训模型。

失败 trajectory 可经人工确认和反向标注后用于评测或训练。存储侧应按风险、访问频率和合规要求分层留存：近期保留完整细节，随后转为压缩摘要，超过保留期后删除或只留聚合指标。具体期限由业务政策决定。

适用场景

  • 生产级长期运行的 agent：跑数月、反复处理同类任务的 agent。哪些失败要记、哪些任务来时要翻出来，是它的核心价值所在。
  • 多租户 SaaS agent：跨租户错位这类高风险失败要做特殊处理——永不淘汰、每次任务启动强制召回、连续多条触发报警。task signature 用"租户加意图"双因子，一个租户的失败不该让另一个租户收到无关提醒。
  • 高风险不可逆操作的 agent：错误代价大、同样的错不能犯第二次的场景。DevOps、金融、合同处理。

已知失效方式

  • 任务一次性、没有重复执行场景却硬上：纯 demo、prototype、一次性脚本，失败被丢弃没问题。失败日记的价值在重复任务，没有重复就没有召回收益。
  • 只使用 free-text：仅记录 task、error 和 timestamp，无法稳定分类和查询。应使用 enum 和受限字段，使失败记录可聚类、可统计。
  • 低价值记录持续累积：如果每次轻微异常都写入 failure journal，召回噪声会随时间上升。可限制自由文本长度，并根据风险、access_count 和 recency 将长期未召回记录归档到冷层。
  • 记下来了但召回不匹配：用 Jaccard 这类粗糙相似度，漏检率太高，记了等于没召回。task signature 之间要用 embedding cosine similarity。
  • 失败记录未经审计直接生效：一条错误的失败记录会让 Agent 在本来正确的路径上反复回避，危害大于没有记录。自动写入的失败记录应先进入待确认状态，经离线审计或人工确认后再进入召回集。（来源：ADPS 记忆模块研讨会 2026-08-05）
  • 高风险失败与普通失败共用策略：跨租户数据泄露和 API timeout 的严重程度不同。高风险失败应独立告警、永久保留，并在相关任务中强制召回。

验证指标

  • 重复失败率：同类任务中重复出现相同失败的比例。应按 failure signature 比较版本前后变化，不能用数据库记录量代替运行结果。
  • 召回率 / 召回命中率：观察相关失败是否被召回，以及召回内容是否与当前任务相关。偏差需要结合漏召回和误召回样本分析。
  • 首次尝试成功率：跟踪 Agent 是否能利用历史 lessons 避开已知错误，并与未注入日记的回放基线比较。
  • 高风险失败计数：跨租户错位等安全边界事件必须独立监控和告警，不设“可接受的小比例”。

最小实现

FailureEntry: failure_id / task_signature / category(enum) / summary
              / root_cause / remediation / lessons[] / access_count
FailureJournal:
    record(entry)          → 重复 failure_id 累加 access_count；超额按 access+recency 淘汰
    by_category(cat)       → 分类查询
    recall_for_task(sig)   → embedding 相似度召回候选，再按风险和相关性重排
    render_for_prompt()    → 格式化注入 prompt（CER 范式：执行前读取相关失败记录）
分层留存：近期全细节 / 中期压缩摘要 / 到期删除或仅留合规允许的聚合指标

生产实现应使用 embedding cosine 计算相似度；在任务启动和高风险工具调用前执行召回，可通过 PreToolUse hook 接入；不同留存层使用相应后端；写入同时执行 schema 校验和基于 access_count 的清理。

场景化示例

设想一个多租户 SaaS 客服 Agent 反复遇到工具错误、跨租户错位、上下文溢出和语义漂移。系统把 boundary_leak 设为最高优先级，按合规要求保留并在相关任务启动时强制召回；task signature 使用“租户 + 意图”，避免把一个租户的失败经验注入另一个租户；候选记录按风险和相关性重排后写入 prompt；UNKNOWN 类先进入 needs_review，经人工审核后再进入正式档案。效果应通过重复失败率、漏召回样本和安全事件复盘验证，不能用预设的改善比例代替。

相邻模式

  • 程序性记忆（M5）：失败日记保存已知失败路径，程序性记忆保存经过验证的成功流程。
  • 进度追踪（M3）：进度追踪维护当前任务步骤，失败日记跨任务保存失败记录。
  • 分层保留（M1）：失败日记是长期记忆层里的专门分区，其分层留存策略正是分层思想在失败档案上的应用。
  • Self-Heal Loop（行动模块）：自愈循环处理当前任务中的失败；失败日记将失败信号持久化并在后续任务中召回。

工程判断

失败日记保留错误现象、错误判断、根因、修复和召回条件。它比单纯的异常日志多出可复用的判断依据，使后续任务能够识别并避开已知失败路径。
