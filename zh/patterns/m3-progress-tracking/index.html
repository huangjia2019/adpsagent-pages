模式简介 在长任务中维护结构化 todo 和状态机，使当前目标、进度、阻塞项与下一步可恢复、可审计。

问题

LLM 依赖 context window 保持当前任务信息，而长上下文中的中间内容容易获得较低注意力。长时间调试会把原计划挤出有效工作集。例如，Agent 完成部分文件后陷入局部缺陷，随后直接进入测试阶段，遗漏计划中尚未创建的文件。

进度追踪将 todos 和状态写入外部存储，并在每轮决策前重新加载。结构化状态同时服务于 Agent 的任务恢复、用户查看和审计。

坐标说明：记忆 × 编排

  • 纵轴 · 记忆：它给 agent 一份"工作日志",跨 step 保留任务上下文，是记忆最简形式（session memory）——记着"我刚做了什么、现在在做什么、接下来做什么"。
  • 横轴 · 编排：进度追踪跨越所有任务步骤，维护统一 todo 状态，用于步骤选择、中断恢复和遗漏检测，因此属于编排层。

解决方案与机制

  1. 精简的状态机：核心 schema 极简——任务描述、状态枚举（pending / in_progress / completed）、进行时形式。状态机的硬约束是任何时刻只有一个 in_progress，单线程 agent 一次只能聚焦一件事。
  2. 状态外部化到对话流：每轮写入进度，并在下一轮重新读取，将任务状态从 context 历史转移到外部存储。
  3. 全部完成时自动清空：所有 todos 完成后清空活动清单，避免旧任务状态影响新任务判断；完成记录可转存审计日志。
  4. 框架层强制 nudge：单靠 prompt 教 Agent 写 todos 不够，框架层还要检测复杂任务未建清单、关闭任务前缺少验证等情况，并按本地策略注入提醒或暂停执行。
  5. 按 agent / session 隔离：每个 agent 或子 agent 维护独立的 todos 池，避免子 agent 的细节 todos 污染主 agent 的高层清单。

适用场景

  • 多步长任务：跨多轮且容易因局部调试遗漏原计划的任务，例如代码重构、多文件改造和复杂调试。
  • 可恢复的长流程：任务可能中途崩溃需要 resume 的场景。进度持久化后，第二次会话读 progress、跳过已完成、从中断步恢复，不重做。
  • 多周持续推进的任务：跨数周对同一目标推进的场景（如投资研究对一只股票的判断），需要双层 todo——高层研究计划跨周保持，会话内具体动作做完合并回高层。

已知失效方式

  • 单次简单任务强行用：纯对话、单次 Q&A 和可以直接完成的小任务通常不需要 todo。
  • 允许多个 in_progress：单线程 Agent 同时保留多个进行中步骤会使当前动作不确定。需要并行时，应拆给多个 Agent 或显式建立并行分支。
  • 缺 active form 字段：UI 显示"正在做什么"时机械地给动词加 -ing，出现"Fix cache bug...ing"这种拼接。用进行时形式字段从写 todo 时就想清楚动词形态。
  • main agent 与 sub-agent 共享一个池：main agent 查看高层清单时被子 agent 的细节 todos 淹没，注意力被无关粒度争夺。子 agent 应使用独立清单，并向上返回结构化进度。
  • 没有框架层 nudge：Agent 执行复杂任务却没有建立或更新 todos，框架也不提醒，进度仍会从工作集消失。nudge 的升级条件要与任务风险和执行权限对应。

验证指标

  • 计划遗漏率：长任务中原计划步骤被跳过的比例。它需要通过回放或任务审计计算，是判断进度追踪是否有效的首要指标。
  • 验证步骤覆盖率：适用任务在关闭前是否包含验证动作。应按任务风险设定要求，并记录 nudge 是否真正改变了行为。
  • resume 成功率：中断后能否从持久化进度恢复，且不重复已完成的不可逆动作。
  • 单 in_progress 合规率：单线程执行器任意时刻只能有一个活动步骤。违反这一不变量说明状态机或并发边界存在缺陷。

最小实现

TodoItem: content（动词原形）/ active_form（进行时）/ status（pending|in_progress|completed）
TodoList（按 owner_id 隔离）：
    start(id)    → 标 in_progress，自动把其他 in_progress 暂停回 pending（一次只一个）
    complete(id) → 标 completed
    all_done()   → 全完成则自动清空
ProgressTracker（框架层强制）：
    context_loss_detected → 复杂任务但没写 todos → 注入 reminder
    nudge 递进：建议 → 要求 → 强制（halting）
    verification_nudge   → 适用任务关闭且无验证步骤 → 追加提醒或暂停关闭
持久化：增量 append-only + 周期 snapshot + session 兜底

生产实现应强制单一 in_progress；复杂度估算可使用成本较低的模型；明确 nudge 从建议、要求到中止的升级条件；TodoList 按 agent_id 隔离。

场景化示例

设想一个买方研究 Agent 持续更新某只股票的判断。SessionState 用严格键值结构记录研究计划、当前投资逻辑、关键风险、反向观点和数据日期；SessionNarrative 用自然语言说明整体目标、本次推进内容和后续写回位置。会话任务完成后合并回高层计划，状态保存为便于 git diff 的 markdown；关键风险和反向观点在每次会话中加载；需要投资经理确认的步骤先进入 needs_review，确认后才能 completed。

相邻模式

  • 分层保留（M1）：Todo list 位于高频更新的会话层，并在每轮决策前加载当前活动项和必要的上层目标。
  • 失败日记（M4）：进度追踪保存任务步骤状态，失败日记保存失败现象、原因和处理结果。
  • Plan-and-Execute（推理模块）：Plan 描述预期步骤，进度追踪维护这些步骤的运行时状态。
  • Hooks Pipeline（治理模块）：框架层的 nudge 和持久化挂点天然契合 hook 机制，可用 PreToolUse / PostToolUse hook 实现。

工程判断

进度追踪为长程任务提供外置工作记忆。它持续保留目标、已完成步骤、阻塞项和下一步，使 Agent 不必从长对话中重新推断当前进度。
