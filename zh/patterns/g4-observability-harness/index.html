模式简介 在 Agent 全生命周期采集 log、metric、trace、cost 和 quality，并跨 Agent 串联 trace。

问题

LLM Agent 的模型权重和内部计算无法像应用源码一样直接检查。系统需要通过 trace 还原模型调用、工具调用、状态变更和 sub-agent 活动。部分 Agent 故障表现为质量和成本持续漂移，而不是在单一时间点抛出异常。

可观测性在每个 LLM call、tool call 和 sub-agent step 采集遥测，并使用同一 trace id 串联 span。完整 trace 用于 root-cause、审计回放、成本归因和产品分析。

坐标说明：治理 × 编排

  • 纵轴 · 治理：可观测性管的是所有 Agent 操作可观测、可重放，是治理的可追溯基础。审批门、爆炸半径、渐进承诺这三件事的记录都要靠它兑现，否则审批 log 没人看、爆炸半径出事没法复盘、信任档位变化没法解释。
  • 横轴 · 编排：单个组件无法看到完整 trajectory。Orchestrator 或 telemetry pipeline 需要跨 Agent、tool 和 step 关联 span，因此属于横切编排。

解决方案与机制

Agent 遥测包含五个维度：

维度 传统软件 LLM Agent 加在哪
Log 应用 log 加 prompt / response / system_prompt 全文
Metric request count / latency / error rate 加 tokens_in / tokens_out / model_swap event / refusal rate
Trace request → service → DB 加 user → agent → sub-agent → tool → LLM call 跨层
Cost 不存在 AI-native：per-call / per-session / per-tenant / per-tool
Quality response status code AI-native：hallucination / scope creep / refusal / correctness

log、metric 和 trace 记录运行事实，cost 和 quality 用于分析趋势。除 threshold crossing 外，还应监测 trajectory slope，例如质量连续下降或每个结果的 token 在多个 cycle 中增长。跨进程使用 W3C Trace Context 的 traceparent 将 span 关联到同一 trace id，并采用 OpenTelemetry GenAI Semantic Conventions。gen_ai.request.model 与 gen_ai.response.model 分开记录，以识别 model fallback。

适用场景

  • 企业 production Agent：需要满足故障分析、客户审计和合规留痕要求。
  • 多租户 SaaS：per-tenant cost attribution 是计费基础，也是跨租户隔离审计的入口。
  • 多 model 系统：model swap 不可见就会变成长时间盲查，request.model != response.model 一查就暴露。
  • 多 sub-agent 或长 conversation 系统：跨 Agent 不串 trace 时，sub-agent 活动和 context 演化无法还原为完整调用链。

已知失效方式

  • Volume Overwhelms Signal（信号被淹）：高流量 trace 会把少量关键异常埋在大量正常 span 中。应对 selected production metric 做 structured alerting，dashboard 看趋势，其余保留采样和 query-on-demand。
  • Trace Sampling Bias（采样偏差）：随机采样可能偏向简单 case，使 dashboard 系统性高估真实质量。应按任务难度、租户、风险和 SLA 分层采样，高风险链路按政策完整留痕。
  • Schema Drift（schema 漂移）：OpenTelemetry GenAI conventions 仍在演进，字段在后续版本中可能改名，进而影响 dashboard、alert 和 cost engine。应使用 schema versioning、dual-write 和 migration window，并跟踪所采用规范的稳定性状态。
  • 自造 observability backend：trace store、query engine 和 dashboard 的建设与维护成本很高。通常可先接 Langfuse、Phoenix 等成熟工具，再补充业务字段和访问控制。

验证指标

  • 五维采集完整度：检查请求、模型、成本、质量和业务结果是否能在同一 trace 中关联。
  • trajectory slope 与 threshold 告警：同时监控绝对阈值和变化率，避免缓慢漂移长期低于固定告警线。
  • 跨进程 trace 串联率：sub-agent span 能否挂回父 trace id。无法串联的调用链应作为采集缺陷修复。
  • 采样难度分布偏差：比较采样集与实际流量在难度、租户和风险上的分布，避免 quality dashboard 偏向简单 case。

最小实现

每个 LLM call / tool call / sub-agent step 产出一个 span：
    填 OTel GenAI attribute（含 request.model 与 response.model 分开）
    cost = compute_cost(span)                 # 按 token 与实际 model 算
    若命中采样 → quality = llm_judge(span)     # hallucination / refusal / scope_creep
    emit 到 OTel pipeline（五维同时打）

跨 sub-agent：主 Agent inject W3C traceparent 到 carrier，
             sub-agent extract 后继续同一个 trace_id

trajectory_slope(tenant, metric, window)：返回变化率，不是阈值
query_for_audit(trace_id)：一个 trace_id 串起所有 span 供监管回放

生产实现将 PRICING 配置为实际模型价格；llm_judge 接入真实的低成本 Judge；business 属性加入 tenant_id、user_id 和 workflow_id；emit 连接真实 collector 或 Langfuse endpoint。

场景化示例

设想一家 Edtech 公司发现作业反馈质量下降，但 application log、请求量、延迟、错误率和传统 APM 都没有异常。团队最终在模型调用记录中发现，一次部署把主 Agent 路由到了能力更低的模型。基础设施指标仍然正常，调用成本甚至下降，只有质量评测同步变差。把 requested model、actual model、cost、quality 和业务结果放在同一 trace 后，model swap 才能被直接定位。

在执行型 Agent 的工程实现里，可观测性可以用统一的活动事件抽象落地：把智能体的每一个活动事件用 Activity 加 Frame 统一表达，开发者就能看到执行过程的完整时间线（如 SSE 实时推送）。需要注意区分一件事——这里的"可观测"是让执行过程对开发者可见，不等于"Agent 对世界的感知"。前者是治理端的 telemetry，后者是感知模块的事。

相邻模式

  • 审批门（G1）/ 爆炸半径（G2）/ 渐进承诺（G3）：审批 log、爆炸半径触发和信任档位变化通过 trace_id 关联到 G4。
  • 钩子流水线（G5）：互补。hook 本身要留痕，Stop hook 常用来挂审计 commit，是 G4 数据采集的入口之一。
  • 推理 / 反思模块的 trace：CoT trace 是 reasoning 维度的可观测性，reflection 讲过的 silent correctness 正是 G4 用 trajectory slope 应对的对象。

工程判断

可观测性主要服务于开发、运营、审计和产品决策。完整 trace 可以缩短影响分析与故障归因时间，并为扩大 Agent 权限提供运行证据。
