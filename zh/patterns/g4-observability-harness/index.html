ADPS Agent 设计模式白皮书

G4 · Observability Harness · 可观测性

以事件、因果、版本、状态差异和外部回执建立 Agent 证据链。

G4 用统一事件、因果标识、版本引用、状态差异和外部回执，把一次运行组织成可以查询、评测和归因的证据链。

v0.4 分类

横切核心 · 观测与证据平面。G4 不再占“治理 × 编排”单格。它贯穿全部认知功能、执行拓扑和生命周期；核心总数仍为 28。

从日志到证据

层需要保留的事实用途
输入与上下文来源、版本、准入和丢弃原因还原 Agent 当时能看到什么
决策与计划目标、步骤、路由、候选和裁决摘要分析漂移、路由和计划错误
动作与控制工具、参数来源、身份、策略、审批和配额审计与调用级归因
状态与结果状态差异、外部回执、业务验收与人工修订识别假成功和真实影响
运行基础模型、提示词、Skill、知识、工具和策略版本版本比较与回归定位

默认保存完整隐式推理既不稳定，也会扩大敏感信息风险。结构化决策摘要、候选、引用、工具调用和状态变化通常更适合作为运行证据。

因果与身份链

principal → agent → workload → session → run → intent
          → approval → model/tool/sub-agent span → resource → outcome

Trace Context 可以传播跨进程 trace，业务对象仍需要稳定 ID。重试会产生新 span，不应因此生成新的业务意图或重复副作用。

三层观察

任务与业务结果回答目标是否完成；Agent 过程回答上下文、规划、工具和恢复是否按合同运行；基础组件回答模型、RPC、存储和策略是否健康。三层使用同一 run、版本和结果引用关联。

运行实例

薪酬付款的证据链包括来源账本、目标合同、Intent、策略裁决、审批视图、等待期间的失效、新批准、工具请求、付款回执、账本状态差异和后续对账。团队因此能区分计划错误、过期审批、重复提交和“接口成功但业务未完成”。

常见失效

  • 记录大量文本，却没有对象 ID、版本和状态差异；
  • 把 HTTP 200 或 exit code 0 当成业务成功；
  • 跨 Agent、队列和回调断链；
  • 采样集中在简单任务；
  • 敏感 prompt 和凭证无限留存；
  • 把 Judge 分数与观测事实混在一起。

验证

检查 trace 连续性、身份与版本完整度、有副作用动作的外部结果确认、孤儿写操作、证据时延、采样偏差和敏感证据访问。测试跨进程、重试、恢复、模型 fallback、schema 升级和 collector 故障。

公开实现

DeerFlow Guardrail展示身份、授权裁决、RunJournal 与工具执行之间的公开代码路径。业务状态差异和外部结果仍由接入方补充。
