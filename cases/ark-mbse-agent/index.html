ADPS Enterprise Agent Systems Blue Book · Case Report 03

Natural Language to SysML: A Modeling Agent That Delivers One Diagram at a Time

The model drafts typed structures within a bounded scope; semantic gates and a single write-back path protect the engineering repository.

Evidence boundary: This report documents the practitioner account of AI4MBSE at Ark (Yage). The case contributor supplied the implementation path, failure observations, and engineering decisions. They have not been independently audited. Illustrations describe interaction and state semantics. Runtime screenshots and demonstration videos are published with the contributor's permission. The data contracts in this report are an ADPS architectural reconstruction of the disclosed mechanisms; they are not the implementation's class or field names.

1. System boundary: the deliverable is engineering state

AI4MBSE runs alongside systems-modeling tools such as MagicDraw and Cameo. Packages, blocks, use cases, states, and relationships enter a shared model repository and may be referenced by later design, simulation, review, and documentation work. An agent write-back changes that shared state.

The model repository and a SysML diagram are separate layers. The repository stores elements and relationships. A diagram projects a selected subset for a particular concern. A diagram can look plausible while the repository contains a dangling reference, an incorrect owner, or a duplicate element. Acceptance therefore has to inspect both repository state and canvas state.

The case assigns two different responsibilities. The LLM interprets a business request and drafts candidate structures. Program logic and the project index own the scope reference, stable identifiers, relationship endpoints, and write authority. These fields can break downstream work when one value is wrong, so the model does not serve as their sole source of truth.

A user requests one diagram in natural language. The system writes a structurally valid, reversible change to a resolved project location. An unresolved scope or invalid structure moves the operation to clarification or blocks it.

2. Running example: create a turnstile use-case diagram

The following request provides a compact example for the rest of the report.

Under the "Turnstile Control" package, create a use-case diagram with three cases: a visitor enters with a card, an administrator opens the gate remotely, and an operations system resets a fault. The visitor and administrator are people; operations is an external system.

The request carries at least four kinds of constraints.

Constraint Content in this example Check
Scope An existing Turnstile Control package The project index resolves it uniquely
Elements Three use cases, two human actors, one system actor, and one subject Count, type, and ownership are complete
Relationships Each actor associates with the corresponding use case Both endpoints already exist
View The subject, actors, use cases, and relationships relevant to this diagram The view is a legal projection of the accepted model

3. Main path: from natural language to typed intermediate representations

An early implementation asked the model to emit elements, relationships, and the view in one response. Four failures recurred: a relationship referred to a name missing from the element list; the same object appeared under near-synonymous names; long context caused omissions late in the response; and the projected view diverged from the repository content. A one-call design reduced call count, but a failed response required the whole structure to be regenerated and provided little stage-level diagnosis.

The current path follows three modeling responsibilities.

Stage Input Output contract The stage must not
Elements Request summary, resolved scope, element allowlist, nearby reusable objects ElementPlan Create relationships or layout
Relationships ElementPlan, relationship allowlist, short business summary RelationPlan Invent an unlisted element or change a stable reference
View ElementPlan, RelationPlan, diagram projection rules ViewPlan Redefine repository structure

The disclosed mechanism implies a job state similar to the following. This is an architecture-level representation, not source code from the product.

ModelingJob
  action: chat | create | modify
  diagram_type: use_case | bdd | ibd | state | ...
  scope_ref: stable project reference | pending
  stage: intent | elements | relations | view | validated | applied
  element_plan: typed elements with stable references
  relation_plan: typed edges whose endpoints resolve
  view_plan: projection over accepted elements and relations
  outcome: applied | applied_with_warnings | blocked | noop
  writeback_receipt: state delta + rollback handle

ADPS interprets ElementPlan -> RelationPlan -> ViewPlan as a chain of typed intermediate representations. An LLM drafts a candidate IR at each stage, and downstream work consumes only an accepted upstream result. The structure has parallels with a compiler front end and semantic checker, and with referential-integrity constraints in a database.

The three stages may run as independent agents or as functions in one runtime. Process count does not determine the design. Context isolation, independent failure semantics, and explicit ownership would be required before the implementation should be classified as a multi-agent handoff.

4. One diagram per operation: transaction and acceptance boundary

"Complete the turnstile model" has no stable completion criterion. It might include package, requirement, use-case, block-definition, internal-block, and state diagrams. An error in an early artifact can propagate through the rest. The case constrains one operation to:

one diagram type + one resolved model scope.

This constraint defines the write set, the acceptance set, the rollback delta, and the smallest reproducible regression test. In software-engineering terms, it combines a Unit of Work with a Command and provides a transaction boundary for implementation and testing.

The case retrospective describes a path that applies a change after deterministic gates pass and exposes one-step undo. The public product description also supports human confirmation before write-back. A deployment can choose either interaction policy according to risk. Both policies should share the same transaction boundary, validation rules, and rollback receipt.

5. Scope resolution and resumable HITL

If the project index cannot uniquely resolve Turnstile Control, the system stops before element planning. When two or three plausible candidates exist, the interface presents them. When none is suitable, it asks for a more precise package or for the package to be created first. It does not silently write to the project root or synthesize a parent-package tree.

This interaction requires a persisted pending operation. It records the resolved action and diagram_type, the missing scope_ref, the current stage, and the options offered to the user. Once the user supplies a package, the runtime resumes that operation rather than performing a fresh full intent classification.

HITL is a resumable transaction in this design. The prompt collects the missing information. Correctness depends on freezing and persisting the job, then resuming from the designated point.

6. Write-back gate: invariants, outcomes, and receipts

The case reports five recurring failure classes: an empty change reported as success, a dangling relationship, an omitted item from an explicit list, a view that diverges from repository content, and an invented scope or reusable object. A deterministic gate checks them through explicit invariants.

Invariant Check Failure handling
Unique scope scope_ref resolves to an existing writable object Clarify or block
Legal types Elements, relationships, and diagram type match the current profile Repair only when the mapping is unique; otherwise block
Reference closure Every relationship endpoint belongs to the accepted or reusable element set Block
Explicit completeness A countable user list matches the accepted plan Clarify before write-back or let the user explicitly skip
View subset Every item on the diagram belongs to the accepted repository result Remove the item or block
Delta consistency A write request produces an observable state delta or an explicit idempotent noop An unexplained empty delta cannot be success
Single writer Repository and view updates pass through one channel that emits a receipt and rollback handle A partial update cannot be reported as complete success

The user-visible outcome can be expressed as four states.

State Write performed Meaning
APPLIED Yes Plan, gate result, and write-back receipt agree
APPLIED_WITH_WARNINGS Yes The main structure is valid; a named non-destructive omission remains
BLOCKED No An invariant failed and project state is unchanged
NOOP No The target already existed, or no writable delta was produced; these reasons are recorded separately

7. Choosing deterministic validation and model reflection

The team tested a generate, model-review, revise, review sequence. Its retrospective lists three problems: the review prompt used criteria that did not match the host schema, latency and model cost increased, and long review prose did not directly improve write-back validity. The team removed the post-write model-review loop. It retained at most one bounded repair before assembly, followed by deterministic admission.

The decision applies under specific conditions.

Error property Suitable mechanism
Type, reference, scope, count, or actual state delta is programmatically decidable Synchronous deterministic gate
The operation has side effects, the user is waiting, and invalid state must be stopped immediately Gate plus transaction receipt
Semantic quality cannot be fully encoded in rules and no side effect has occurred Generator-critic review or human review
A failure becomes visible only across runs Failure journal, experience replay, or offline analysis

Validation and reflection can coexist. This case assigns write-back admission to deterministic checks. It does not establish that structured artifacts never benefit from reflection. Offline review can still help analyze omission patterns, improve diagram profiles, and assess modeling granularity. Selection depends on decidability, side effects, repair window, and latency requirements.

8. Type-equivalence layer: align planning vocabulary with the host metamodel

The team found that an import layer can collapse a fine-grained relationship type into a coarser host type. The LLM may plan with a domain-specific name, the host API may use a metamodel name, and the write-back result may return another normalized label. Direct string equality can reject a legal result or admit a coarse type into the wrong diagram profile.

A stable implementation needs an explicit type-equivalence layer.

planning type
    -> canonical domain type
    -> host metamodel type
    -> write-back type returned by the tool

The mapping is selected by diagram profile and host adapter. It retains both original and normalized types for diagnostics and regression tests. This confines host differences to adapters and profiles instead of distributing domain-term guesses throughout orchestration code.

This detail matters because the resulting log can look like an LLM type error when the defect is in deterministic semantic adaptation. Without the mapping trace, a team may classify an adapter bug as hallucination and tune prompts that were not responsible.

9. Context construction and model routing

As a project grows, full rules for all diagram types, complete chat history, and the entire project tree should not enter every model call. The case uses five controls.

  1. Inject only the active diagram profile.
  2. Produce one stable business summary; relationship and view stages consume the summary and accepted upstream IR.
  3. Layer project context. Distant context carries project constraints and session progress; local context carries a bounded projection of nearby packages, blocks, and reusable elements.
  4. Route intent, clarification, and simple structure filling to a lighter model where appropriate. Reserve the primary model for element and relationship planning. Use rules for view selection when the profile is deterministic.
  5. Vary execution depth by diagram complexity while keeping write-back invariants common across routes.

These controls reduce the input surface of each decision. The contributor reports better stability and cost than the earlier one-response design followed by whole-operation retries. Public materials do not include comparative token, latency, or success-rate data, so this report records that statement as practitioner evidence rather than a measured result.

11. Evaluation protocol: published evidence and missing measurements

The published material shows the architecture path, selected intermediate structures, and write-back inside a real host tool. It does not establish long-term reliability across projects, diagram types, and concurrent users.

Claim Current public evidence Evidence status
Consultation requests can bypass the modeling path Intent log with action=chat and no generated JSON One runtime record
Relationship write-back uses stable structural identifiers Relationship and endpoint log One runtime record
The assistant is embedded in a modeling tool and completes multi-turn demonstrations Host screenshot and two videos Visual evidence
The three-stage chain is more stable and less expensive than one-response generation Contributor retrospective No published comparison data
Gates reduce dirty writes over time Failure classes and corresponding controls No longitudinal incident data

A later version should record the following measures on a fixed test set. Results should be stratified by diagram type, create versus modify, novice versus expert interaction, and host adapter.

Measure Definition
Scope-resolution accuracy Proportion of automatically resolved scope_ref values confirmed by a reviewer
Explicit-element recall Proportion of user-named elements present in the accepted ElementPlan
Escaped dangling references Invalid relationship endpoints discovered after write-back; target is zero
Silent scope-expansion incidents Unapproved package creation, ownership movement, or writes to the wrong scope
False-success rate Operations reported as successful with an empty receipt or failed structural acceptance
Clarification-resume accuracy Clarifications that preserve the operation and diagram type and resume from the correct stage
Rollback completeness Undo operations that restore both repository and canvas state
Stage cost Tokens, latency, retries, and model cost for intent, element, relationship, and view stages
Gate quality Block rate, false-block rate, and bounded-repair success by rule

This protocol turns a working demonstration into comparable system evidence. The next evidence revision should prioritize these measurements over additional architectural adjectives.

13. Shared finding and variation across three case reports

All three ADPS case reports move high-precision structural coordinates out of model-generated prose. Their execution and validation timing differ.

Case Program-owned coordinates Validation timing Repair window
Report 01: Dongfang Yiteng Business identifiers, state provenance, workflow nodes Before and after workflow steps and business calls In-session suspension, approval, and resumption
Report 02: Xuanxu Technology Workspace, store, SRS, bounding box, and pipeline state External probes in a static six-stage pipeline Runtime rule fallback and cross-run failure records
Report 03: Ark (Yage) Scope, stable identifiers, relationship endpoints, and type mappings Pre-write gate in an interactive turn Bounded repair, clarification, blocking, or rollback

These reports support an engineering proposition for further testing: precise structural coordinates should travel through traceable program state, which remains authoritative; model output supplies a candidate plan. Three independent cases make the proposition more useful, but they do not constitute a statistically validated industry result.

The variation also improves pattern selection. Choose validation according to external observability, side effects, user wait time, and the repair window. A programmatically decidable error belongs in a synchronous gate. An error visible only after execution belongs in outcome verification. A pattern that emerges across runs belongs in a failure journal or offline review.

14. Transfer boundary and SysML v2

The design fits systems whose outputs enter a governed repository, carry type and reference constraints, can affect existing engineering assets, and pass through controllable tool interfaces. Parts of EDA, BIM, ERP master data, CMDB, and manufacturing process planning share these conditions. A transfer should preserve four structures: typed IR, stable references, deterministic validation, and a single write channel with a receipt.

The complete gate is unnecessary for reports, slide decks, and open-ended retrieval outputs where a flawed result can be regenerated at low cost. Two additional limits apply. First, the public evidence comes mainly from demonstration projects and is not certification for a large safety-critical deployment. Second, the available material does not cover concurrent team writes, model-branch merges, permission partitions, or compensation for long transactions.

OMG finalized SysML 2.0 in 2025 together with work on the Systems Modeling API and Services. SysML v2 adds a more precise semantic foundation, textual notation, and standardized model-access mechanisms. OMG also expects SysML v1 to remain in use during a multi-year transition. AI4MBSE therefore needs to accommodate established desktop toolchains and newer SysML v2 environments. A standard API can reduce proprietary adapter surface, but it does not remove scope resolution, reference integrity, profile policy, or transaction receipts. See the OMG SysML 2.0 specification and OMG's SysML release overview.
